## A. Kiến trúc dự án

### A.1. Mô hình tổng thể — 3 tầng, server là "trọng tài"

```
TikTok LIVE ──(tiktok-live-connector v2, sign qua Euler)──┐
                                                          ▼
                                   server.js  (Express + ws, 6.041 dòng)
                                   ├─ normalize event (user, uniqueId, avatar, coins…)
                                   ├─ LiveEventEngine: queue theo loại + dedupe + priority
                                   ├─ LikeBatcher: gộp tim theo cửa sổ 3/5/10/15s
                                   ├─ GiftComboTracker: chỉ tính repeat mới
                                   ├─ Actions.*: mutate state (authoritative)
                                   └─ broadcast: temple.event / temple.state (throttle 350ms)
                                                          │
                                          WebSocket JSON-RPC 2.0 (/ws)
                                                          ▼
                         public/index.html (stage 9:16 1080×1920)
                         ├─ js/live.js      : RPC controller + HUD + fit stage
                         ├─ js/game.js      : ShopGame (canvas 2D, 2.313 dòng)
                         ├─ js/audio.js     : WebAudio SFX + hàng đợi TTS
                         ├─ js/music.js     : playlist 8 track
                         ├─ js/particles.js : hearts/confetti/firework
                         ├─ js/announcer.js : MC tự động (BroadcastChannel)
                         └─ js/conversations.js + js/reactive-seller.js
                                                          ▲
                                     BroadcastChannel      │ (music, announcer, crowd metrics)
                                                          │
                                              public/admin.html (3.258 dòng, 17 card)
```

**Nguyên tắc quan trọng:** server quyết định **sự thật** (điểm, VIP, đơn hàng, text TTS). Browser chỉ **render + phát âm thanh**. Đây là điểm rất tốt để tái sử dụng: Tarot phải rút bài ở server, không rút ở client.

### A.2. Giao thức & bus nội bộ

- JSON-RPC 2.0 qua **cả** HTTP `POST /rpc` và WebSocket `/ws` (dùng chung `handleRpcCall`, dòng 5546+).
- **Notification (server → client):**
  - `temple.state` — snapshot công khai, gộp tối đa 350ms (`scheduleStateBroadcast`).
  - `temple.event` — 1 sự kiện gameplay (gift, serve, join, leave…).
  - `temple.viewerCount`, `tts.play`, `tts.status`, `shop.reset` (soft/hard).
- **Client → server:** mọi nút bấm = 1 RPC (`shop.join`, `live.connect`, `shop.leave`, `shop.viewerServed`…).
- Bảo vệ tải: bỏ qua client có `bufferedAmount > 2MB` (dòng ~5957).
- Method namespace: **`shop.*` / `game.*` mới + `temple.*` legacy vẫn chạy** (alias). Rất thuận lợi: có thể thêm `tarot.*` mà không phá automation cũ.

### A.3. Luồng một sự kiện gift (ví dụ đầy đủ)

1. `WebcastEvent.GIFT` → chuẩn hoá `giftCoins = gift.diamondCount`, `groupId`, `repeatCount`.
2. `queueTikTokEvent('GIFT', …)` → `LiveEventEngine.push` (dedupe theo `msgId:groupId:repeat`).
3. `handleQueuedEvent` → `processGiftEvent` → `GiftComboTracker.apply()` lấy `delta`.
4. `coinTier(coins)` — **khớp chính xác** 1/5/10/15/20/25; giá trị khác **bị bỏ** (không tạo đơn).
5. `Actions.giftOrder` cập nhật `state.*`, `supporter`, `viewer` (VIP 25/50/100), celebration 25/50/100/500, enqueue đơn vào `viewer.orders`.
6. `pushEventLog` → `broadcastNotification('temple.event')` + state throttled.
7. `live.js` → `game.handleEvent` (hoạt cảnh), `audio.playCoin`, banner, `audio.enqueueTts(ev.ttsText, {profile…})`.

### A.4. Lưu trữ trạng thái

- `data/game-state.json`: aggregate (served, drinks, tips, likes, supporters, settings, voiceProfiles, conversations, reactive, likeBatching). Ghi debounce 1s.
- **Không** lưu: `tiktok` state, danh sách viewer đang hoạt động (chỉ trong RAM, `viewerSessions` Map, giữ 15 phút sau khi rời).
- Cache TTS: `data/tts-cache/` + `data/kokoro-cache/` (đều gitignore).

## C. Hiện trạng tính năng

### C.1. Đang hoạt động (đọc code + test xác nhận)

- **TikTok LIVE**: connect/disconnect, kiểm tra live trước khi mở WS, chống double-connect, auto-reconnect 5 lần backoff 4→30s, liveness error rõ ràng, viewer count.

Requirements

Root cause
Tracing Admin → server.js → public/js/conversation.js showed the configured value was never lost; it was misapplied:

The countdown started at synthesis, not at audio end. startLine() set nextAt = Date.now() + intervalMs() when the conversation.speak RPC resolved — that happens as soon as Kokoro finishes generating, seconds before the clip finishes playing. So the real gap after the audio was interval − clipLength, and with a short clip plus a retry it collapsed to a few seconds.
Every temple.state broadcast could re-base the countdown. applySnapshot() ran on every state push (gifts, likes, settings) and reset nextAt from "now" whenever the interval value differed in type or timing, restarting the wait — and if a stale 5 s-ish deadline was in play, lines bunched up.
A reading release used a 4 s shortcut (Date.now() + 4000) rather than the normal interval, so post-reading dialogue came back almost immediately.
Every open stage tab had its own independent countdown, so two tabs (OBS source + preview) could interleave their lines a few seconds apart. The server only blocked identical text.
Changes

lastSpeechEndedAt is recorded when the clip actually ends; nextAt = lastSpeechEndedAt + intervalMs().
New waitForSilence() keeps the engine in "speaking" state until the shared TTS queue reports idle (bounded to 45 s so a blocked clip can't stall forever), then schedules.
New scheduleFrom(anchor) — the only way the deadline is computed. applySnapshot() re-bases on the last speech end, never on "now", and only when the interval genuinely changed. notifyReading(false) uses the same helper.
A server busy response now waits retryInMs instead of recording a line and restarting the interval.
server.js

oracleLeaseUntil reserves the Oracle voice for one full interval after each successful line, so a second stage tab gets {ok:false, busy:true, retryInMs} instead of speaking its own line.

Phase 1 — Kokoro performance
What the code showed: kokoro_worker.py is one persistent Python process reading JSON lines from stdin and synthesising one request at a time. Sending clips concurrently from Node would only queue them in the worker's stdin, so it cannot speed anything up (and would risk out-of-order audio). Measured cost is ~13–22s per 1–2 sentence clip on one CPU thread, and most of a reading is unique text that can never be cached.
