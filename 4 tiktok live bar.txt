```
            resolveGiftRule()                  (config/gifts.json: byGiftId → byGiftName → diamondBands)
            sessionPlayers / sessionVipScores / metrics
            broadcast(event)                   (all WS clients)
  → Unity : TikTokWebSocketClient.ReceiveLoopAsync() → ConcurrentQueue<string> inbox
  → TikTokWebSocketClient.Update() : JsonUtility.FromJson<TikTokEvent> → EventReceived
  → TikTokGameController.HandleEvent()
        PlayerManager.Handle()  → PlayerActor.AddGiftPower() / ApplyAction()
        GiftEffectManager.Play()
        ClubCameraController.Focus()/FocusFireworks() ; PlayerManager.FocusPlayer()
  → PlayerActor (SpriteRenderer + SpriteFlipbook + TextMesh + Sprite banners)
    GiftEffectManager (runtime Light + runtime ParticleSystem)
    TikTokGameController.OnGUI (IMGUI banner/HUD)
```

Details that matter:

- **Gift normalisation** (`normalize-tikfinity-event.js`) reads `giftId`, `giftName`, `giftType`, `repeatCount`, `repeatEnd`, `unitDiamondCount`, `giftPictureUrl`, and computes `diamondCount = totalDiamondCount ?? unitDiamonds * repeatCount`.
- **Master rules win over gift config**: `rules.js:resolveMasterRule()` first matches `rule.giftId === event.giftId`, then name/comment triggers; `applyRule()` writes `action`, `durationMs`, `label`, `variant`, `fireworkBursts`.
- **Gift config fallback**: `server.js:resolveGiftRule()` — `giftConfig.byGiftId` (currently `{}`), then `byGiftName[].aliases` (diacritics stripped via `normalizeGiftName`), then `diamondBands` sorted by descending `minimum`.
- **Dedupe** (`isDuplicate`): `eventId` kept 10 min, otherwise composite key 2.5 s.
- **Gift library**: every real gift (`isRealObservedGift`) is persisted to `config/observed-gifts.json` (cap 500) and can **auto-bind a Gift ID to a master rule** with a matching trigger (`learnObservedGift` → writes `master.json`, broadcasts `master_config`).
- **Unity receives the whole broadcast** but only consumes `status|member|chat|gift|like|follow|share|snapshot|reset`. `config`, `metrics`, `gift_catalog`, `gift_observed`, `viewer_guide` are ignored by the game (they are Control-Panel messages) — verified by grep of the `type` comparisons in `PlayerManager.Handle` and `TikTokGameController.HandleEvent`.
- **`TikTokEvent` has no `giftPictureUrl`/`unitDiamondCount`/`repeatEnd` fields**, so even though the bridge sends them, JsonUtility drops them. The game never renders a TikTok gift image.

## 4. GifPlayer implementation (Phase 3)

`UnityProject/Assets/Scripts/GifPlayer.cs`, namespace `TikTokLiveBar` (note: **not** `TikTokLiveGame`).

- **Discovery:** `Directory.GetFiles(FrameDirectory, "*.png")` then `Array.Sort(files)` (GifPlayer.cs:41-44). Exactly one directory, supplied by the caller; no recursion, no GIF parsing.
- **Decode:** per file `File.ReadAllBytes` → `new Texture2D(2,2,RGBA32,false)` → `tex.LoadImage(bytes)` → `tex.Apply(false, true)` (non-readable). `yield return null` every 20 frames (GifPlayer.cs:52-65).
- **Timing:** `Update()` accumulates `Time.deltaTime` and advances in a `while (frameTimer >= 1/FrameRate)` loop, writing `targetRenderer.sharedMaterial.mainTexture` each step (GifPlayer.cs:69-88). Uses **scaled** time (pauses if `Time.timeScale == 0`).
- **Looping:** `currentFrame = (currentFrame + 1) % frames.Length` — always loops; there is no play/stop API.
- **Transparency:** material is built from `Shader.Find("Unlit/Transparent")` (fallback `Sprites/Default`), so PNG alpha is preserved (GifPlayer.cs:23-27).
- **Caching / multiplicity:** no cross-instance cache — each `GifPlayer` loads its *own* copy of every frame. Several instances would multiply VRAM. Only one instance exists today (`CreateDjPerformer`).
- **Cleanup:** `OnDestroy` destroys all `Texture2D`s. The `Material` created in `Start()` is **never destroyed** (leak on scene reload).
- **Failure handling:** missing directory / zero PNGs → `Debug.LogWarning` and no frames (component stays enabled, does nothing). **A corrupt PNG is silent** — the return value of `LoadImage` is ignored, so `frames[i]` stays a 2×2 placeholder. `targetRenderer == null` would throw in `Start()` (code-read inference, not exercised).
- **Cost:** 475 frames × 720×405 × 4 B ≈ **553 MB of uncompressed RGBA texture memory**, plus an 18 MB burst of `byte[]` garbage during load, with main-thread `LoadImage` hitches every 20 frames.

## 5. Gift mapping system (Phases 4-5)

Two layers exist and they are **not** asset mappings:

**Layer A — bridge (data):** `config/master.json` rules (giftId/trigger → `action`, `durationMs`, `label`, `variant`, `fireworkBursts`), then `config/gifts.json` (`byGiftName` aliases, `diamondBands`).

**Layer B — Unity (behaviour):** `action` drives `PlayerManager.ApplyAction()`; `diamondCount` drives `GiftEffectManager`; `label` becomes a `TextMesh` title; nothing selects a file by `giftId`.

- **Default gift behaviour:** always one of the `diamondBands` (lowest `minimum` is 1), so *every* gift produces something.
- **Unknown gift:** never "missing asset" — it degrades to `dance`, 3 s (`diamondBands` last entry).
- **Simultaneous gifts:** no queue, no scheduler. Each event runs immediately and independently; the banner is a single slot that the newest gift overwrites (`GiftEffectManager.BannerText` / `BannerUntil`). Fireworks/spotlights stack concurrently.
- **Priority:** implicit only — camera focus is last-wins (guarded by `cinematicVersion` in `TikTokGameController.CinematicGift`), spotlight/fireworks are additive, size is governed by `topRank`/`GiftPower` (`PlayerActor.GiftPowerScale`, capped at +18 %).

- **Repeats:** handled upstream — `repeatCount` is folded into `diamondCount` in the normaliser; duplicate `eventId`s are dropped server-side.
- **Fallbacks:** wings sprite → `energy-wings-v2`; `title-{variant}` may be null (then the banner is hidden); empty `Sprite[]` → invisible dancer; avatar download failure → NPC fallback sprite chosen by FNV hash of the userId (`StableAvatarIndex`).

## 6. Rendering & layout (Phase 6)

- **Camera:** built at `(0, 7.2, 14.2)` looking at `(0, 1.25, -1.2)`, FOV 45, solid dark background (`ClubSceneBuilder.Build`); `ClubCameraController` holds `defaultPosition (0,9.2,17.2)` and `focusWideBasePosition (0,7.2,14.2)` and drives focus/cinematic shots.
- **Everything is 3D world-space.** No Canvas, no `RawImage`, no `SpriteRenderer`-only 2D layer: characters/avatars/wings/banners are world-space `SpriteRenderer`s with billboarded rotation toward `Camera.main`; names/ranks/titles are world-space `TextMesh`.
- **HUD/banners** are IMGUI in `TikTokGameController.OnGUI()`: `GUI.matrix = Scale(scale)`, gift banner `GUI.Box(new Rect(width*0.5f - 310f, 142f, 620f, 68f), giftEffects.BannerText, bannerStyle)` shown while `Time.unscaledTime < BannerUntil`.
- **Sorting:** `PlayerActor.Initialize` sets `characterRenderer.sortingOrder = Mathf.RoundToInt((12f - position.z) * 100f)`; wings `-2`, banner `+8`, avatar `+12`, title shadow `+13`, title `+14`, rank `+15`. Materials come from `GameMaterials.Sprite()` with `_ZTest = Always` and `renderQueue = 3200`, so **depth testing is effectively off** and ordering is purely `sortingOrder`.
  ⚠️ With the camera at +Z looking toward −Z, front-row dancers (z ≈ +3.75) get order ≈ 825 while rear rows (z ≈ −3.65) get ≈ 1565 — i.e. **rear rows are drawn last/on top**. That looks inverted; flagged as a suspected bug, not visually confirmed.
- **Effect placement:** fireworks at random `x ∈ [-6.5, 6.5], y ∈ [4, 8.2], z ∈ [-7, -0.5]`; cold fountains at fixed x = ±5.35, ±3.45, ±1.55, `y = 0.08`, `z = -4.75`, rotated `(-90,0,0)`; spotlights track `actor.position + (0,7,2)` and `LookAt(actor)`.
- **Overlap:** additive by nature (no depth test, multiple `Light`s, particle systems) — no z-fighting resolution beyond `sortingOrder`.
- **Different positions:** yes for fireworks/spotlight/camera; banner and HUD are fixed rectangles.
- **Removal:** `Destroy(fountain, duration + 1.5f)`, `Destroy(burst, 1.8f)`, spotlight `Destroy` at the end of its coroutine; player decorations are toggled via `Renderer.enabled`, never destroyed; particles auto-destruct with their GameObject.

## 8. Performance analysis (Phase 7) — bottlenecks from the code

1. **VRAM: ≈553 MB** for the DJ GIF alone (475 × 720×405 RGBA32, no mips, non-readable). This is the single largest cost and is paid at every launch.
2. **Load hitch:** 475 synchronous `File.ReadAllBytes` + `LoadImage` calls, yielding only every 20 files; expect a multi-second startup hiccup plus ~18 MB of transient garbage.
3. **Material/draw-call explosion:** `PlayerActor.Initialize` calls `GameMaterials.Sprite()` four times (character, wings, banner, avatar) and `CircularAvatar()` once — each call creates a **new `Material` instance**. With `maxPlayers: 400` that is up to ~2 000 materials with `renderQueue 3200` / `ZTest Always`, which defeats batching.
4. **TextMesh count:** 4 `TextMesh` per actor (name, rank, title, shadow) → up to 1 600 dynamic meshes, each rebuilt when text changes (`ShowTitle`, rank updates).
5. **Per-frame actor work:** every `PlayerActor.Update` does `Camera.main`, reads `characterRenderer.sprite.bounds`, applies alpha to 8 renderers, and rotates 6 transforms toward the camera → hundreds of ops per frame at 400 players.
6. **Per-gift allocations:** each firework burst creates a GameObject + `ParticleSystem` + 2 material clones (`sharedMaterial` and `trailMaterial`) and is destroyed after 1.8 s; fountains likewise. A gift storm creates/destroys dozens of systems per second (GC churn).
7. **Combo dictionary never pruned:** `GiftEffectManager.combos` grows one entry per distinct `userId` for the whole session.
8. **Avatar cache never evicted:** `AvatarService.cache` holds every downloaded 256×256 texture for the session (≈100 MB at 400 users), 4 concurrent downloads, 10 s timeout.
9. **`Resources.Load` inside refresh paths:** `PlayerActor.RefreshDecorations` re-loads wings/banner sprites on every evolution/focus change (cached by Unity, but still a lookup + `Sprite.bounds` work per gift).
10. **GIF texture swaps** happen in `Update` at up to 30 fps on the main thread; assigning `sharedMaterial.mainTexture` each frame also mutates the shared material.
11. **Frame pacing:** `targetFrameRate = 60`, `vSyncCount = 0` — a 400-dancer scene with fireworks will be CPU/draw-call bound long before GPU fill-rate.
12. **Server side** is lean: dedupe map capped at 2 000, observed gifts at 500, per-socket `bufferedAmount > 512 KB` terminates slow clients, 32 KB `maxPayload`, rate-limited messages.

*(No profiler run was made — these are code-derived costs, with the VRAM figure computed from dimensions × 4 bytes.)*

## 10. How to add new gift visuals (Phase 8) — exact procedure

**Config-only (no rebuild, no code)** — changes *behaviour*, never artwork:
- Edit `TikTokBridge/config/master.json` (or use Control Panel → Master Rules, which broadcasts `master_save`) to set a rule's `giftId`/`trigger`, `action`, `durationMs`, `label`, `variant`, `fireworkBursts`. Actions available: `join, dance, camera, change, walk, grow, medal, vip, topdj, fireworks` (`src/master/rules.js:ACTIONS`).
- Edit `TikTokBridge/config/gifts.json` (`byGiftId`, `byGiftName[].aliases`, `diamondBands`) — read once at bridge start, so **restart the bridge**.
- The bridge auto-learns Gift IDs from live traffic (`observed-gifts.json`) and can bind them to a trigger-matching rule automatically.

**Any new *artwork* requires C# changes + a Unity rebuild** — there is no data-driven asset resolver. Concretely:
- **New GIF gift:** split the GIF into PNG frames (e.g. `LiveAssets/GIFT_<name>/frame_000.png…`), then in `GiftEffectManager.Play` (or a new component) create a Quad with `GifPlayer { FrameDirectory = …, FrameRate = … }` keyed by `data.giftId`; destroy it after N seconds. Rebuild required.
- **Static PNG gift:** `Resources.Load<Sprite>("Gifts/<name>")` (put the PNG under `Assets/Resources/Gifts/`), instantiate a `SpriteRenderer` billboarded to the camera; no import settings special-casing needed beyond Sprite type. Rebuild required.
- **Sprite-sheet animation:** split the sheet into frames under `Assets/Resources/Characters/<name>/NNN.png`, add `<name>` to `CharacterLibrary.Names`, and drive it with `SpriteFlipbook.SetFrames(frames, fps)`. Rebuild required. (This is exactly how dancer characters work.)
- **Custom Unity animation:** no Animator pipeline is wired at runtime — you would add an `Animator`/`Animation` component yourself, or animate procedurally as `PlayerActor` does. Rebuild required.
- **Gift with multiple effects:** combine an `action` (movement/camera/title) with `fireworkBursts` and `diamondCount` thresholds; for a bespoke composition, add a coroutine in `GiftEffectManager` that sequences sprite/particle/light beats. Rebuild required for the composition; `fireworkBursts`/`label`/`durationMs` remain config-tunable.

- **A2 — Timing was dropped, not derived.** Unity plays characters at `Random.Range(10f,14f)` fps (fixed 15 fps for `hanhan_video_dance`) — see `PlayerActor.ChangeCharacter()`. That ignores per-GIF delays (e.g. `a.gif` is 25 fps, `mushroom_dance_09` is 5 fps, `g.gif` claims 100 fps). So the converter exported **frames only**, never duration metadata — consistent with the PNGs having no `tEXt` chunks.
- **A3 — Composited frames.** Hashes match after disposal compositing, so extraction used the fully-rendered frame, not raw sub-rect patches.
- **Unknown:** why 20 were skipped; whether the converter was a one-off local tool that never got committed (most likely) and whether it still exists on the author's machine.

## 6. TASK 5 — Unity character loading, exactly

**Folder discovery:** there is none. `CharacterLibrary` holds a hardcoded 13-string array; a new folder in `Resources/Characters/` is invisible to the game until someone adds its name to that array and to `PlayerActor.BottomPaddingFraction()`. That hardcoding is why exactly the 13 converted folders exist: the code and the asset set were kept in lockstep by hand.

**Frame loading:** `Resources.LoadAll<Sprite>($"Characters/{name}")` → `.OrderBy(sprite => sprite.name, StringComparer.Ordinal)` → cached forever in a static `Dictionary<string, Sprite[]>`. Discovery of *which* frames exist is delegated to Unity's Resources index (all sprites under that folder), so any `*.png` added there is picked up — but ordering depends on `000.png` zero-padding, which the source set uses up to 3 digits (`039.png`). A 4th digit or an unpadded name would silently reorder.

**Frame sequencing:** `SpriteFlipbook.SetFrames(frames, fps)`; `Update()` advances with `Time.deltaTime * playbackSpeed` (1.5× idle, **2.7× while dancing/jumping/celebrating**), random phase offset per actor (`clock = Random.value / fps`) so the crowd desynchronises. Cycling is a modulo loop, no ping-pong, no events.

**How characters change on a gift:** they usually don't. Chain:

1. `TikTokGameController.HandleEvent` → `playerManager.Handle(liveEvent)` → `PlayerManager.Handle` `type == "gift"` → `actor.AddGiftPower(diamondCount)` + `ApplyAction(actor, data, duration)`.
2. `ApplyAction` switches on **`data.action`** (a server-side rule field), never on `giftId`:
   - `"change"` → `ChangeCharacter()`
   - `"walk"` / `"jump"` / `"grow"` / `"camera"|"vip"|"topdj"|"fireworks"|"medal"` → Celebrate
   - default → `Dance(...)`
3. `ChangeCharacter()` → `CharacterLibrary.RandomCharacter(characterName)` → **uniformly random among the other 12**; fps `10–14` random (15 for hanhan).

**Does a gift ID select a character animation?** **No.** Grep confirms `giftId` appears only in event plumbing (`TikTokEvent.cs`, `src/tiktok/normalize-event.js`, `src/security.js`, `config/*.json`) and never indexes an asset. The only gift that *can* change a character is the rule in `config/master.json` (`gift-tiktok-change`, **giftId `5269` "TikTok"**, `action: "change"`) — and even that yields a **random** character. Chat `doi nv` / `đổi nv` / `đổi nhân vật` does the same (`config/game.json` aliases, matched by `command.Contains("doi nv")`).

**Does `GiftEffectManager` touch art?** No. `GiftEffectManager.Play` builds a text banner + combo counter, spaws a spot `Light` (`Spotlight`) and procedural `ParticleSystem` bursts/fountains (`CreateBurst`, `CreateColdFountain`), audio from `Resources/Audio/dragon-studio-fireworks-07-419025`. **Zero `Resources.Load` of any character or GIF asset.** Gift visuals today are lights, particles, a camera focus (`ClubCameraController.Focus`) and the actor's own flipbook speeding up.

## 9. Can these assets be reused for a dedicated gift-animation system?

**Yes, and unusually cheaply — the hard part (matching art, alpha, proven converter, provenance) is already done.**

Strengths: 33 transparent GIFs / 634 frames; a proven lossless extraction path (95 frames bit-identical today); a working runtime PNG-sequence player (`GifPlayer`) that already feeds a quad with `Unlit/Transparent` at a configurable fps; a gift→rule engine server-side that already carries arbitrary fields to Unity; alpha-preserving import rules; and documented licences (`sources.json`, `LICENSE:31`).

Constraints to design around:
- **Two sizes exist.** 20 GIFs were never converted; the 13 characters are capped at 256 px, so reusing *those* PNGs as full-screen overlays will look soft (the sprites are also `TextureImporterCompression.Compressed`). For gift overlays, re-extract at source resolution rather than reuse the 256-px set.
- **Timing was thrown away.** FPS must come from the GIF's own delays (compute at conversion time and write a sidecar) — `a.gif` is 25 fps, `mushroom_dance_09` is 5 fps, `g.gif`/`l.gif` delays are corrupt. Do not inherit the character system's random 10–14 fps.
- **Memory.** `GifPlayer` loads *every* frame as a full `Texture2D` up front (475 frames × 720×405 ≈ 555 MB RGBA). Fine for one DJ loop, not for 33 overlays. Use an `Addressables`/spritesheet atlas or an LRU ring of ~64 decoded frames, or stream from the existing `/assets/gifs` mount.
- **Licensing.** Art is third-party (Sina/Weibo, Sohu, Giphy, weilegetu, qiubiaoqing, diydoutu). A monetised/live-streamed overlay should keep `sources.json` attribution intact and prefer the Giphy-sourced `boss_monster`-style items where terms are clearest.
- **The dead endpoint is a free win**: `/assets/gifs/*.gif` is already served, so a browser/OBS overlay could consume the library with **zero** server changes.

- **No hot reload**: a built player bakes `Resources` at build time, so newly converted animations need a rebuild; in the Editor they appear after a reimport/restart. Refresh-without-restart is not supported.
- **Average-FPS playback**: per-frame delays are stored but `SpriteFlipbook` plays at constant FPS.
- `defaultDurationMs` is metadata only — Unity does not consume it yet.
- FPS/speed edits apply the next time an actor loads that animation, not to a currently animating one.
- **Deleting an animation only removes the Unity folder**, not the source GIF (kept by design); a later conversion sweep will recreate it.
- No user accounts: protection is loopback + same-origin + control header, not authentication.

## 1. Three programs, one contract

```
TikTok / TikFinity ──WS──▶ Node bridge (server.js) ──WS──▶ Unity overlay
                              ▲      │
                       HTTP/WS│      │ files on disk
                              │      ▼
                        Control panel   UnityProject/Assets/Resources/Characters
```

- **Node bridge** (`TikTokBridge/server.js` + `src/`) — the only program that talks to TikTok and the only one that writes files.
- **Control panel** (`public/`) — a browser client; it has no privileges beyond the bridge's checks.
- **Unity overlay** (`UnityProject/Assets/Scripts`) — never calls TikTok and never reads GIFs; it connects to the bridge as a `role: "overlay"` WebSocket client and reads converted PNG folders from `Resources`.
- **`scripts/`** are offline tools; they do not talk to Unity at all (see §5).

## 2. What `server.js` is

One Express + `ws` server on loopback (default `127.0.0.1:3000`). In order:

1. `.env` is loaded, config JSON read (`game.json`, `gifts.json`, `master.json`, `observed-gifts.json`), paths resolved (`GIFT_ANIMATIONS_CONFIG`, `BACKGROUND_CONFIG`, `GIF_SOURCE_DIR`, `UNITY_CHARACTERS_DIR`…).
2. Security middleware: host allow-list, CSP, `X-Frame-Options: DENY`, `nosniff`, no-store for `/api/*` and `.html`.
3. Static files: `public/` (panel), `/assets` (so `a.gif`, `mushroom_*.gif` etc. are reachable as previews), `/vendor/three`, plus `/backgrounds/*` which serves media from `LiveAssets` and `DJ_VIDEO` through a path rebuilt from the folder root.
4. REST API: health/config/gifs/backgrounds, gift-mapping save, and the GIF Manager routes.
5. WebSocket server with two client roles: `control` and `overlay` (Unity).
6. Live provider connection (TikFinity Desktop by default, or `tiktok-live-connector`).
7. The demo/Test Live timer machinery.
8. Shutdown handlers.

Every inbound TikTok-like event goes through the same funnel:

```
normalize → processGameEvent → sanitize → master rules → gift rule
          → gift→animation mapping (adds animationEffect / animationCharacter)
          → emitGameEvent → dedupe → sessionPlayers/metrics → broadcast() → all WS clients
```

`broadcast()` is literally "serialize once, send to every open socket"; `broadcastToRole('control'|'overlay', …)` is used for panel-only status and Unity-only commands like `remove_players`.

### From GIF to Unity animation

`scripts/convert-gifs.js` (or the bridge's own watcher) calls `src/gifs/pipeline.js`:

1. Read `assets/gifs/*.gif`, decode with `gif-decoder.js` (own decoder, no native deps), get frames/delays/transparency.
2. `sanitizeAnimationId('Mushroom Dance-01.gif') → mushroom_dance_01` — lowercase, accents stripped, non-alphanumerics collapsed to `_`, ≤ 64 chars. **This is the name Unity will use later.**
3. Write `000.png…N.png` + `animation.json` into `UnityProject/Assets/Resources/Characters/<animationId>/` via a staging folder + rename, so an interrupted conversion never leaves half an animation.
4. Rebuild `Characters/animations.json` — the manifest Unity reads (`animationId`, `frameCount`, `fps`, `loop`, `playbackSpeed`, `transparent`, `width/height`, `durationMs`).
5. Write `logs/gif-conversion.log` and `logs/gif-conversion-report.json`, update `.conversion-state.json`.

`server.js` starts the same pipeline as a debounced, single-flight watcher when `GIF_AUTOCONVERT !== '0'`.

## 4. What `src/` does (and why it never “sends” to Unity)

`src/` is pure logic used by `server.js`:

- `src/gifs/*` — decoder, PNG encoder, pipeline, manager, manifest.
- `src/gifts/animations.js` — the allow-list of built-in effects (`dance`, `jump`, `walk`, `change`, `grow`, `spotlight`, `fireworks`, `party`), mapping sanitation, and `resolveAnimationTarget(id)` → either `{effect}` or `{character}`.
- `src/tiktok/*` — normalisers for TikFinity messages and raw connector events.
- `src/master/rules.js` — trigger/action rules (`join`, `camera`, `vip`, `medal`…).
- `src/background/registry.js` — background catalogue/validation and URL building.
- `src/security.js` — host/origin checks, event sanitising, rate limits.

None of it opens a socket. **The only transport to Unity is `server.js`'s WebSocket `broadcast` plus the files the pipeline writes.** That is deliberate: Unity sees one JSON event schema no matter where the event came from.

## 5. `scripts/` → Unity: through the filesystem only

`convert-gifs.js` writes PNGs + `animations.json` into `Assets/Resources/Characters/`. Unity then discovers them at runtime:

- `CharacterLibrary` loads `Resources/Characters/animations` (the manifest) and `Resources.LoadAll<Sprite>("Characters/<id>")`, ordered by sprite name (`000.png`, `001.png`…), caching per id.
- A few folders are also hard-coded as `BuiltInNames` so an animation still works if the manifest is missing.
- Metadata drives `FpsFor`, `LoopFor`, `SpeedFor`.

So the answer to “how do scripts send control to Unity” is: **they don't — they publish assets and a manifest, and Unity polls them when it starts**. New conversions appear after the next Play/load (the manifest is cached on first use).

## 6. Panel → Unity over the WebSocket

The panel registers as `control`. `handleClientMessage` decides what a control client may do:

- `set_username`, `disconnect_tiktok` — connect the live provider.
- `demo_start`, `demo_stop`, `demo_event`, `reset_game` — Test Lab / Test Live.
- `master_save`, `master_test`, `set_gift_animations`, `test_gift_stop` — control-only (overlays are rejected).
- `set_background` — validates, persists, then broadcasts `background_config`.

Commands mostly mutate server state and then **broadcast the resulting event to overlays**:

- `demo_event` → `emitDemoAction` → mock user (e.g. `demo-9`) → `processGameEvent`.
- `set_gift_animations` → saved + broadcast `gift_animations` to control; from then on every gift is decorated with the mapping.
- `set_background` → `background_config` to overlay, Unity downloads the media from `/backgrounds/...` and replies `background_ack`, which the server records and forwards to control.
- `test_gift_stop` → removes exactly the `gif-test-*` avatars via `remove_players`.

Unity's `TikTokWebSocketClient` registers as `overlay`, heartbeats (`ping`/`pong` every 2 s, 7 s timeout), reconnects every 2 s, queues JSON into a `ConcurrentQueue` and dispatches on the main thread → `TikTokGameController.HandleEvent`.

## 7. TikTok Live → Unity

Two interchangeable providers (`LIVE_PROVIDER`):

- **TikFinity** (default): a WebSocket to `ws://127.0.0.1:21213/`; each message is normalised by `normalize-tikfinity-event.js` (accepts many field spellings, nests, and repeated messages in one payload).
- **`tiktok-live-connector`**: `member`/`chat`/`like`/`follow`/`share`/`gift` events normalised by `normalize-event.js`; gift streaks of type 1 that haven't ended are suppressed so a combo becomes one event; `extendedGiftInfo` is off, so gift details come from TikFinity/catalog.

Both end in `processGameEvent`, exactly like demo events. Reconnect uses exponential backoff (2 s → 30 s). This means **Unity cannot tell a real gift from a demo/test gift** — that is why the wire format carries `testEvent`-derived fields and why the Test Live path reuses it.

## 8. How a *name* turns into the animation on stage

The chain, concretely:

1. Gift arrives: `giftId = "5655"`, `giftName`, `diamondCount`.
2. `processGameEvent` applies master rules (action/duration) and then the mapping:
   `resolveGiftTarget(giftAnimationMappings, giftId, animationRegistry)`.
   - Catalog hit → `event.animationEffect = "fireworks"`, `animationDurationMs`.
   - Converted-folder hit → `event.animationCharacter = "tenor"`.
3. `emitGameEvent` broadcasts that event; `sessionPlayers` is updated so the avatar exists.
4. `PlayerManager.Handle` → `GetOrCreate` → `PlayerActor.Initialize` → `ChangeCharacter()` picks a **random** character from `CharacterLibrary.Names` for a brand-new viewer (built-ins + everything in the manifest).
5. `TikTokGameController` then calls `giftEffects.Play(liveEvent, actor)`:
   - `PlayMappedAnimation`: if `animationCharacter` is set → `actor.PlayAnimation(id)`; else `animationEffect` → dance/jump/walk/change/grow/spotlight/fireworks/party.
6. `PlayerActor.PlayAnimation(id)`:

   - `flipbook.SetFrames(frames, FpsFor(id, 12), …)`, `SetLoop(LoopFor(id))`, `ResetPlayback()`;
   - rescales the body to the sprite height (`2.15 / sprite.bounds.size.y`), sets `Dance` state, returns `true`.
7. `SpriteFlipbook.Update` advances frames at `fps * playbackSpeed`, holding the last frame when `loop` is false.
8. Controller sends `animation_ack {eventId, animationId, ok}` only for events that carried an animation; the bridge accepts it only from an overlay and only for event IDs an active Test Live session sent, then forwards it to the panel.

Naming pitfalls worth knowing:

- **The name is the folder name** (`Characters/tenor/`). Rename in the GIF Manager rewrites the folder *and* the mappings; deleting removes mappings. Nothing else keys on display names.
- `CharacterLibrary` will silently ignore an id with no folder, and `PlayerActor` will refuse to switch — that's the “mapping points at a deleted animation” case.
- `PlayerActor.BottomPaddingFraction()` hard-codes a few ids (`a`, `b`, `h`, `mushroom_dance_01`…) to align feet; an unknown/new id gets `0`, which can float the sprite slightly.

## Where the choice happens

Server never assigns a GIF. It just sends a `member`/`chat`/`gift` event with a `userId`. Unity decides the look when it creates that viewer's actor:

`PlayerManager.Handle` → `GetOrCreate` → `Create` → `PlayerActor.Initialize` → `ChangeCharacter()` → `CharacterLibrary.RandomCharacter(characterName)`

`RandomCharacter` is literally:

```csharp
string[] choices = Names.Where(name => name != except).ToArray();
string name = choices[UnityEngine.Random.Range(0, choices.Length)];
```

At spawn `characterName` is null, so it is a **uniform random pick over the whole list** — not a hash of the userId, not their TikTok avatar, not first-come order. Two viewers can get the same GIF; one viewer can get a different one every time they re-enter. The TikTok profile picture is a separate small circular sprite next to the name, not the dancer.

The pool is `CharacterLibrary.Names`:
- hard-coded `BuiltInNames` (`a`, `b`, `c`, `d`, `e`, `g`, `h`, `j`, `k`, `mushroom_dance_01`, `mushroom_dance_15`, `mushroom_magic_02`, `hanhan_video_dance`), plus
- every folder in `Characters/animations.json` (the manifest the converter writes).

Duplicates are removed, so right now that is all ~34 converted animations — including `tenor` and anything you import later. **A newly converted GIF immediately starts showing up randomly on new joiners.**

## But a join alone usually creates nobody

`config/master.json` has `joinMode: "keyword_only"`, and `processGameEvent` marks a new, non-chat, non-gift viewer as `spectatorOnly`. `PlayerManager.Handle` then returns before creating an actor. So:

| First action | Avatar + random GIF? |
|---|---|
| Just joins the live | **No** — counted in metrics only |
| Chats the join keyword (`hey`) | Yes (`chat-hey-join` rule, action `join`) |
| Sends any gift | Yes (`giftAlwaysJoins: true`) |
| Follows / shares | Yes |
| Chats/likes after already being known | Already has one |

That is why you can have 200 people “in the room” and only the ones who interacted on the floor.

## How long they keep it

- While the actor exists, the GIF is **sticky** — nothing re-randomises it per event.
- Unity removes non-NPC actors after `playerTtlSeconds = 600` (10 min without activity), and the bridge prunes its roster after `playerTtlMs = 600000`; at 400 concurrent players the oldest is removed first (`RemoveOldest`).
- Rejoin after removal, `reset_game`, a demo reset, or restarting Play mode → new actor → **new random GIF**.

## What changes it afterwards

1. `change` action — gift `5269` (“tiktok”) has the master rule `action: "change"` → `actor.ChangeCharacter()` → random *different* GIF. Same for chat `đổi nv` / `doi nv` / `đổi nhân vật`.
2. Any gift mapped to a converted GIF in the GIF Manager (`gift 5655 → tenor`): `GiftEffectManager.PlayMappedAnimation` sees `animationCharacter` and calls `actor.PlayAnimation("tenor")`. The wing images never travel from `server.js` to Unity at runtime. Unity loads its **own copies** from `Resources`, and the bridge only sends the *numbers and actions* that decide whether an avatar earns them.

## 1. Two copies of the same artwork

```
TikTokBridge/assets/banners/wings-fire.png      ← source / served at /assets/banners/...
UnityProject/Assets/Resources/Banners/wings-fire.png   ← what the game actually uses
```

`server.js` exposes the first folder only through `app.use('/assets', express.static(assetsDir))`, which is for the panel/preview. **No game code fetches that URL.** There is also no copy script anywhere in the repo — the duplication is manual authoring (the README in `assets/banners` calls them “source renders … generated for Cloud Disco”).

Unity loads them by resource path, not by network:

```csharp
string wingsAsset = giftFocused ? "Banners/energy-wings-v2" : $"Banners/wings-{variant}";
wingsRenderer.sprite = Resources.Load<Sprite>(wingsAsset)
    ?? Resources.Load<Sprite>("Banners/energy-wings-v2");
```

`CharacterTextureImporter` (an editor `AssetPostprocessor`) forces every PNG under `Resources/Banners/` to Sprite / Single / 180 PPU / uncompressed / max 2048 / `alphaIsTransparency`, so `Resources.Load<Sprite>` works and the wings keep a consistent scale.

## 2. The actual “who gets a wing” logic

It is entirely in `PlayerActor.RefreshDecorations()`:

```csharp
bool decorated = giftFocused || topRank > 0 || GiftPower >= 10;
string variant = topRank == 1 || GiftPower >= 1000 ? "royal"
    : topRank == 2 || GiftPower >= 200 ? "fire"
    : topRank == 3 || GiftPower >=  50 ? "neon"
    : "ice";
```

So:

| Condition | Wing shown |
|---|---|
| Currently in a gift-focused spotlight | `energy-wings-v2` (not the fire/ice/neon set) |
| Top donor #1, or ≥ 1000 diamonds | `wings-royal`… but no royal file exists → falls back to `energy-wings-v2` |
| Top donor #2, or ≥ 200 diamonds | `wings-fire` |
| Top donor #3, or ≥ 50 diamonds | `wings-neon` |
| Any gift power ≥ 10 | `wings-ice` |
| No focus, not top-3, < 10 diamonds | wings disabled |

Alongside them, the banner uses `Banners/title-{variant}` and only renders when the title text is non-empty. Note `wings-royal.png` **doesn't exist** in `Resources/Banners` (only `title-royal.png` does), so rank 1 / 1000+ diamonds deliberately falls back to the focus wings.

## 3. Where those inputs come from (this is the server’s part)

**`GiftPower`** — cumulative diamonds per viewer:

- `server.js` keeps it in `sessionPlayers[userId].giftPower` and ships it in `snapshot.players[]`;
- Unity also adds it live: `PlayerManager.Handle` → `actor.AddGiftPower(data.diamondCount)`.

It survives as long as the actor does (10-minute TTL), so wings are a “spending history” decoration, not a per-gift effect.

**`topRank`** — `TikTokGameController` calls `UpdateTopPlayers()` on `gift` and `snapshot`; the top three donors by diamonds get ranks 1–3, podium positions and `wings-fire`/`neon`/royal-fallback.

**`giftFocused`** — the controller sets focus for events whose action is `camera`, `walk`, `vip`, `topdj`, `fireworks` or `medal`:

```csharp
playerManager.FocusPlayer(liveEvent.userId, focusSeconds);
```

`FocusPlayer` dims everyone else and calls `SetGiftFocus(true)` on that actor; `RefreshDecorations` then switches to `energy-wings-v2`, scaled at least `0.55`, for the focus duration (2.5–12 s), then restores the normal state.

So the “rosa → CÁNH VIP” rule in `master.json` (gift `8913`, action `medal`, label `CÁNH VIP`, `variant: "fire"`, 60 s) behaves like this: +10 gift power → `wings-ice` + “TÂN BINH” title; during the camera focus → `energy-wings-v2`; after focus → back to ice unless the viewer is also top-3 or has 50/200+ diamonds.

## 4. Important gap: `variant` from the config is not used for wings

`server.js` does send it (`event.variant = giftRule.variant`, and stores `titleVariant` in the snapshot), and `TikTokEvent` / `TikTokPlayerData` both have the field — but `RefreshDecorations()` computes its own `variant` from rank and gift power and never reads `data.variant`/`titleVariant`. Consequences:

- setting `"variant": "fire"` on a master rule changes nothing visually today;
- a gift mapped to a converted GIF also does not change the wings;
- the wing tier is purely a donation/rank ladder.

If you want “this gift gives fire wings for 60 s”, that has to be wired from `event.variant`/`titleVariant` into `RefreshDecorations` (and given its own timeout), rather than editing the PNGs.

## 5. Practical notes

- To see fire wings on stage: give a test viewer 200+ diamonds (Test Lab gift 200, or a `giftPower` ≥ 200 snapshot), or make them rank 2.
- `player-wings.png` exists in both folders but **nothing in Unity references it**; only `energy-wings-v2`, `wings-fire/ice/neon`, and `title-*` are loaded.
- To add a new wing tier: drop `wings-<name>.png` into `Assets/Resources/Banners/` (the importer handles settings), then extend the `variant` switch. Copying it into `TikTokBridge/assets/banners/` only matters if you also want it served at `/assets/banners/...` for previews.
- Because there is no sync step, replacing `TikTokBridge/assets/banners/wings-fire.png` alone has **zero effect** on the game — the file in `Assets/Resources/Banners/` is the one that ships.

## Phase 3 — How the system is supposed to work

1. `RuntimeBootstrap.StartGame()` (a `[RuntimeInitializeOnLoadMethod]`) creates the camera, calls `ClubSceneBuilder.Build()`, then adds `PlayerManager`, `TikTokWebSocketClient`, `GiftEffectManager`, `TikTokGameController`.

This is not one bug — it is four independent blockers, and the first two are decisive.

### 1. Everything the viewer looks at uses an **unlit shader**

| Visible element | Material / shader | Receives light? |
|---|---|---|
| Dancers (body, wings, banner) | `GameMaterials.Sprite()` → `CharacterSprite.shader` with **`Lighting Off`** | **No** |
| DJ performer (the big GIF) | `GifPlayer` → `Unlit/Transparent` | **No** |
| Backdrop (4 quads) | `Unlit/Texture` (fallback `Sprites/Default`) | **No** |
| Laser/beam `LineRenderer`s | `GameMaterials.BackgroundSprite()` → same unlit sprite shader | **No** |
| Avatars | `CircularAvatar` material (separate unlit-style shader) | No |

A Spot light physically cannot brighten a fragment shader that never samples lighting. The dancers, the DJ and the backdrop look **identical** whether the lights are on, off, red or blue.

### 2. The only lit materials are on a layer those lights **exclude**

28 stage objects (`DJ Stage Deck`, steps, booth, speakers, panels) are built with `CreateLitBox()`, which does `box.layer = 8`. `AddLight()`, `AddDjKeyLight()` and strobes all set:

```csharp
light.cullingMask = ~(1 << FloorLightingLayer);   // everything except layer 8
```

So the 3 point washes + 2 keys + 4 strobes illuminate **exactly none of the stage geometry they were built for**. Only the 4 enabled moving heads and the transient gift spotlight (`cullingMask = -1`) can touch the deck — and those are aimed at the crowd.

### 3. `ClubPulseController` zeroes the disco lights

`DiscoLight` components are created with `intensity = 0` and only set their intensity in `Update()`. `ClubPulseController.Start()` runs first and caches every light except `Moving Head*` / `Strobe Light*` — including all 8 `Disco Light` entries — at **base intensity 0**. Its `Update()` then writes:

```csharp
state.Light.intensity = state.BaseIntensity * (0.72f + pulse * 0.55f);  // = 0
```

`DiscoLight.Update()` writes 1.4–3.6 in the same frame. With no script execution order defined (`ProjectSettings/MonoManager.asset` does not exist), the two fight every frame; the visible result is either 0 or flicker, never a reliable sweep. This is a concrete bug, not a design choice.

### 4. Aim and placement point away from the stage

After the `ClubRoot` z = −12 shift, the stage deck sits at z ≈ **−19.3**, DJ at **−19.5**, backdrop at **−22**. But:

- Disco lights `LookAt(sweepX, 0.1, sweepZ)` with `sweepZ ∈ [−3.5, 3.5]` → they sweep the **audience**, 12–16 m in front of the stage.
- Strobes `LookAt(x·0.3, 0.7, 0.8)` → also the audience.
- The 3 point lights are created *after* the shift, so they stand at z = 1, 0, −7 — up to 20 m in front of the deck.

### Secondary contributors

- **No floor to catch light or shadow.** `Invisible Dance Floor` has `Renderer.enabled = false`; character sprites can’t cast shadows (unlit shader has no shadow-caster pass); no realtime GI/lightmaps (`m_BakeOnSceneLoad: 0`, realtime GI off). So no pools of light, no shadows, no bounce.
- **Emission dominates.** `ClubLit` materials are authored dark with strong `_EmissionColor` (stage strips 0.55, pixels 0.72). The scene reads as “lit” from self-illumination, which masks any real light contribution.
- **Ambient setting is inert.** `RenderSettings.ambientLight = (0.15, 0.02, 0.05)` is applied while the scene’s ambient mode is **Skybox** (0), so the assignment is ignored — ambient comes from the default skybox, not the intended dark red.
- **8 duplicate disco lights** (loop inside `AddDjKeyLight`, called twice) sit at identical positions with identical names; they double intensity but do not widen coverage, and they make the Hierarchy read as if there were four.
- **Per-object pixel light limit**: Ultra allows 4 pixel lights; with 21 light components the rest fall back to vertex/SH, so even lit surfaces get weak, blotchy response.
- **16 of 20 moving-head light components are disabled** (`castsLight` only true for `index % 3 == 0`); those fixtures are decorative beams only.

**Root cause, stated plainly:** the lights are real and mostly enabled, but the game’s entire visible stage — dancers, DJ, backdrop, beams — is rendered unlit, while the only lit shader (Standard via `ClubLit`) is used exclusively on layer-8 objects that these lights are configured to ignore. The disco set that could add colour is additionally zeroed by `ClubPulseController`, and its aim points at the audience rather than the stage.

## Root causes

### MC voice was too quiet

- The old WAV processing only added up to **+3 dB** and limited the signal by peak level. It did not normalize perceived loudness, so Kokoro output was much quieter than the DJ music.
- Unity’s `AudioSource.volume` is capped at `1.0`; once configured at 100%, there was no remaining gain available in Unity.
- Different providers produced different levels, and music ducking was happening around an already quiet voice.

The new chain:

1. TTS WAV is generated.
2. RMS is normalized toward **−20 dBFS**.
3. Configurable output gain of **0–18 dB** is applied.
4. A soft peak limiter keeps output below full scale.
5. The processed WAV is cached once.
6. Unity applies only the configured `volume`; there is no second gain stage.

### Autonomous MC did not speak

- The existing random MC used a **150–300 second** timer.
- It had no LIVE-session lifecycle hook.
- It did not track activity timestamps or reset an idle countdown.
- It was not driven by `chat`, `gift`, `follow`, `share`, `member`, or `like` activity.
- During testing I also found and fixed an empty-queue pump loop that could starve the idle timer after the first announcement.
