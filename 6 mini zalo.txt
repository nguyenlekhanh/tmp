## 2\. Người dùng tự chọn nơi lưu dữ liệu

Đây là phần mình thích nhất trong ý tưởng của bạn.

1\. Lưu trực tiếp trên điện thoại / máy tính

Local

- Tin nhắn và danh bạ lưu trong SQLite.
- File ảnh/video lưu trên máy.
- Không cần thuê server.
- Có thể dùng offline.
- Nếu mất máy mà chưa backup thì có nguy cơ mất dữ liệu.

2\. Google Drive

Cloud backup

- Backup tin nhắn, hình ảnh, file.
- Khôi phục khi đổi điện thoại.
- Đồng bộ dữ liệu giữa các thiết bị qua cơ chế riêng.

Lưu ý: Google Drive nên dùng để backup/restore, không nên dùng như database chat trực tiếp vì dễ phát sinh xung đột khi nhiều thiết bị cùng ghi dữ liệu.

3\. NAS / ổ cứng mạng

Private storage

- Synology, QNAP hoặc NAS tự dựng.
- Lưu ảnh, video, tài liệu.
- Có thể chạy server riêng bằng Docker.
- Truy cập từ điện thoại và máy tính khi ở ngoài nhà.

4\. Server riêng – Big Boss

Enterprise

- Mỗi người có tài khoản riêng.
- Đồng bộ tin nhắn theo thời gian thực.
- Quản lý nhóm, phân quyền, nhiều thiết bị.
- Mở rộng hàng nghìn hoặc nhiều người dùng hơn tùy cấu hình.
- Tự quản lý dữ liệu và hạ tầng.

Điểm quan trọng: Không cần chọn một nơi lưu duy nhất cho toàn bộ ứng dụng. Có thể lưu tin nhắn trong database, file trên NAS, backup lên Google Drive và đồng bộ qua server. Người dùng được chọn cấu hình phù hợp.

# 2. Gradle là gì?

Bạn hỏi rất đúng. Mình giải thích đơn giản nhé.

Hãy tưởng tượng bạn đang xây một căn nhà:

Gradle không phải ngôn ngữ lập trình.

Gradle là hệ thống Build Automation, chịu trách nhiệm:

- Tải và quản lý thư viện cần thiết.
- Biên dịch Kotlin.
- Xây dựng các module.
- Chạy kiểm thử.
- Đóng gói APK/AAB.
- Quản lý cấu hình build.

Ví dụ khi chạy:

powershell

```powershell
.\gradlew assembleDebug
```

Gradle sẽ xây dựng ứng dụng Android và tạo file APK debug.

### 1. Library verdict

**libsignal** is the recommendation: it is the only maintained option with **PQXDH (Kyber1024 + X25519)** *and* **Double Ratchet**, official Android AAR (minSdk 23, four ABIs), and 0.103–0.106 releases through late 2026. Blocking conditions, stated plainly:

- **Licence:** declared AGPL-3.0-only in its POM. A distributed KONNEX becomes an AGPL combined work and must publish source. **The repo currently has no `LICENSE`/`NOTICE` file at all** — this must be resolved first. No commercial licence exists for libsignal.
- **Build risk:** the AAR is compiled to **Java 21** bytecode with desugaring; this build runs **JDK 17 / AGP 8.7.3**, so D8's acceptance of class-file v65 must be verified (V-1).
- **Fallback:** **vodozemac** (Apache-2.0) — real Double Ratchet, but **no PQXDH and no Kyber**: Olm's triple-DH handshake is explicitly *not* equivalent to Signal's PQXDH, and there is no official standalone Android artifact, so KONNEX would own a Rust/UniFFI build pipeline.
- **OpenMLS** (MIT) is documented as the future group path: MLS is epoch/tree-ratcheted, not Double Ratchet, and standard ciphersuites are not post-quantum.
- Rejected with reasons: libolm (deprecated 2024), libsignal-protocol-java (GPL, unmaintained), primitives-only libraries (would require designing a protocol ourselves), Proteus, OpenPGP.

Audit status is reported as found: protocol-level academic analyses exist for X3DH/Double Ratchet/PQXDH; **no complete public third-party audit of the libsignal implementation was found**; libolm had a 2016 NCC audit, vodozemac none that I could confirm.

### 2. Database encryption

SQLCipher Community (BSD-style) via Room `SupportOpenHelperFactory`; 32-byte random DB key in SQLCipher **raw-key** form, wrapped by a non-exportable Keystore AES-256-GCM key and stored outside the DB. Migration is export → `cipher_integrity_check` + `integrity_check` + row-count comparison → atomic swap with `.plain.bak` retained three verified opens → cleanup; a marker outside the DB makes every interruption point resumable or rollbackable. Includes WAL checkpointing to avoid plaintext residue, startup `cipher_version` assertion, and a rule that the plaintext DB is never deleted before a verified encrypted open.

**Decision needed:** current SQLCipher 4.20 pairs with `androidx.sqlite` 2.7/Room 3, while this project pins **Room 2.6.1**; either pin an older SQLCipher or schedule a Room upgrade milestone — `AGENTS.md` forbids a casual bump.

### 3. E2EE v1 scope

### 4. Backups

### Repository findings that change the plan

1. **The DB is a lazy process-wide singleton opened from a startup coroutine** (`AppContainer.database` → `KonnexApplication.onCreate`), and WorkManager **auto-initializes** (`androidx.startup.InitializationProvider` confirmed in the merged manifest) — so `SyncWorker`/`BackupWorker` can open the DB in a fresh process with no UI. Migration must therefore run **inside the first DB open**, behind a gate; a splash-screen migration alone is insufficient.
2. **No migrations exist yet** (Room v1, one exported schema, no destructive fallback) and there is **no raw SQLite/file access** anywhere — one builder call to change.
3. 9 entities / 9 DAOs, 15 DB consumers, 6 `withTransaction` call sites, all going through `RoomDatabase` → unaffected if the factory is wired once.
4. **`AndroidKeystoreCipher` only handles Strings** — it needs a byte-array wrap (or base64 reuse) plus an AAD-bound key for the DB key; today there is no rotation API.
5. **Backups are an unencrypted ZIP containing message bodies.** DB encryption would not protect them; that gap is now called out as a release condition, not a footnote.
6. Attachments live as plaintext files in `filesDir/attachments` — outside this milestone's coverage, also stated.

### Failure cases added beyond the earlier proposal

Keystore key **missing** vs **permanently invalidated** (separate paths), disk-full before rename, marker-lost-but-files-present (adopt state by content sniffing), `.bak` + encrypted DB both valid, double migration attempts, downgrade to a pre-SQLCipher APK (unreadable DB), worker-starts-before-migration, and the deliberate plaintext window — tightened from "keep `.plain.bak` for 3 opens" to **delete immediately after the first verified encrypted open**, since a lingering plaintext copy is worse than a rollback that user backup can cover.

### Migration safety verdict

Structure is sound; four hard changes are required:

1. **WAL is the dangerous part**: checkpoint → assert 0-byte WAL → delete `-wal`/`-shm` **before and after** the swap, or plaintext pages survive the migration.
2. **Deleting `.plain.bak` after the first encrypted open is insufficient.** Replace with a two-launch checkpoint: open + `cipher_integrity_check` + `quick_check` + row-count receipt → `CONFIRMED_PENDING_RESTART` → next cold start re-verifies → only then delete.

### Encryption architecture

- **Tink streaming AEAD** `AES256_GCM_HKDF_4KB` (AES-256-GCM with HKDF-SHA256 and 4 KiB segments). No custom cipher or framing.
- **One independent random Tink keyset per attachment**; never shared with SQLCipher, backups, other attachments, or tokens.
- Keysets are wrapped with a dedicated non-exportable Keystore key, alias **`konnex.attachment.wrap.v1`**.
- Files: `files/attachments/<id>.konnexatt` plus `<id>.konnexatt.key`.
- **16-byte versioned header** `KONNXAT1` / version 1 / algorithm 1 / flags 0.
- Header plus `(attachmentId, ownerId, formatVersion, mimeType)` is authenticated as Tink AAD. The key sidecar is wrapped with the same metadata under a separate key-AAD tag.
- Incremental 64 KiB processing; temp file → fsync → atomic move. Plaintext attachments are never written to persistent storage.
- `read()` is limited to 32 MiB in memory; larger data uses `openDecrypted()` streaming.
- Legacy plaintext paths are rejected; there is **no plaintext fallback**.
- Read-only, non-exported `AttachmentContentProvider` streams decrypted bytes through a pipe under a per-URI grant.

### Migration and recovery

`AttachmentMigration` runs at startup before normal work:

1. Process semaphore + cross-process file lock.
2. Durable journal under `noBackupFilesDir`, atomically rewritten at every phase.
3. Preflight duplicate paths, root containment, size/SHA-256, and free-space check.
4. Generate/install the wrapped key sidecar.
5. Stream-encrypt to temp, fsync, verify plaintext digest.
6. Authenticate the encrypted temp file and compare against the row.
7. Atomically install ciphertext, update the Room path.
8. Delete plaintext only after verification and row update.
9. Resume interrupted cleanup by re-verifying the ciphertext.
10. Surface explicit `KEY_UNAVAILABLE`, `LOW_STORAGE`, or `RECOVERY_REQUIRED` states. Corrupt/duplicate/out-of-root/orphan cases preserve originals.

A final-review fix now also validates an already-encrypted row’s key sidecar, so a missing key cannot be reported as “Enabled.”

### Backup integration

- Phase 2.2 container is unchanged; inner archive schema is now **2** (schema 1 still restores).
- Encrypted attachment ciphertext and raw Tink keysets are stored **inside** the authenticated `KONNXBK2` container.
- Attachment keys remain independent of backup DEK/KEK, SQLCipher, and other attachments.
- Restore unwraps in memory, generates a fresh local key, re-encrypts for the target owner, verifies size/SHA-256, then imports. No plaintext attachment reaches disk.
- Missing/corrupt attachments are skipped or marked failed without aborting message restore.

## What was built

**Fresh-install recovery engine** (`BackupRecoveryEngine`) that never touches `backup_records`:
- **Sources:** a SAF document the user picks (`ActivityResultContracts.OpenDocument`) or any `.konnexbackup` discovered in a configured, readable destination (`provider.list("konnex-backups")`).
- **Two unlock methods:** passphrase (Argon2id) or the 160-bit recovery key (HKDF) — exactly one, and only the slot the container actually has. Credentials are wiped after every step and never persisted, logged, or sent anywhere.
- **New container primitive:** `EncryptedBackupContainer.checkCredential` unwraps the DEK and wipes it without walking the body, so "wrong passphrase" and "damaged container" become distinct typed outcomes (`WRONG_CREDENTIAL` / `INVALID_RECOVERY_KEY` vs `CORRUPT_CONTAINER`). Format, AADs and limits are unchanged — existing `KONNXBK2` backups stay valid.
- **Flow:** stage → inspect public header → unlock/authenticate → verify every chunk+footer → parse/validate archive → preview (counts, attachment coverage, local conflicts) → explicit confirmation bound to the container's SHA-256 fingerprint → re-authenticate → re-encrypt attachments under fresh local keys → one Room transaction with in-transaction read-back → decrypt every restored attachment again to verify → typed result.
- **Crash safety:** non-secret `restore-journal.json` (fsync + atomic replace, phases `STAGED`/`PREPARED`/`ATTACHMENTS_WRITTEN`/`COMMITTING`/`COMMITTED`/`FAILED`), an OS `FileLock` (`restore.lock`), and `recoverInterrupted()` which deletes `-restored-` files no row references. A crash can leave extra files but never a row pointing at a missing file, and success is never reported before verification.
- **Compose flow:** select → credential entry → preview → progress with typed step labels → completion summary, with typed errors and retry to the failing step. Entry point added to Backup settings so it exists on a new install.

Also fixed a real reporting defect found by the new tests: `RestoreReport.missingAttachments` always reported 0 because it queried the table after inserting the `MISSING` row (Medium, now counted against what the archive actually carried).

Implement Phase 2.6 of KONNEX: eliminate memory-bound backup and restore operations while preserving the existing encryption architecture, backup compatibility, database integrity, and crash-recovery guarantees.

## 2\. Streaming Encrypted Container

Preserve the existing `KONNXBK2` format and backward compatibility.

Implement streaming APIs for:

- Container creation.
- Container authentication.
- Container decryption.
- Credential verification.
- Container inspection.
- Passphrase rewrapping.
- Recovery-key rewrapping.

Requirements:

- AES-256-GCM.
- Existing 64 KiB chunk format.
- Existing authenticated header, chunk ordering, final markers, and footer.
- Existing Argon2id parameters and HKDF-SHA256 derivation.
- Unique nonces.
- Strict chunk ordering and truncation detection.
- Authenticate every chunk and footer before considering the container valid.
- Never expose unauthenticated plaintext to archive parsing or database import.
- Preserve existing recovery and passphrase behavior.

Do not silently introduce a new backup format.

If a format change is unavoidable, introduce an explicit new version and retain readers for existing backups.

## 3\. Streaming Backup Export

Replace the current in-memory export pipeline.

Required pipeline:

`Room data → bounded archive writer → streaming encrypted container → temporary encrypted file → verified destination`

Requirements:

- Stream attachment content instead of materializing attachment byte arrays.
- Use bounded buffers.
- Avoid writing plaintext archive files to persistent storage.
- Do not retain the complete ZIP or container in memory.
- Verify encrypted output before publishing it.
- Use temporary encrypted files and atomic publication where supported.
- Clean up incomplete files after errors.
- Preserve existing backup metadata and attachment integrity.
- Do not delete an existing valid backup if a new backup fails.

Define and enforce explicit maximum limits for:

- Individual attachment size.
- Total archive size.
- Number of archive entries.
- Entry names and metadata lengths.
- Total decompressed size.

Prevent ZIP bombs, duplicate entries, path traversal, and integer overflow.

## 4\. Streaming Restore

Replace the current memory-bound restore path.

Required pipeline:

`Selected source → encrypted container verification → authenticated streaming decryption → bounded archive parser → staging → verified Room import`

Requirements:

- Do not parse archive data before container authentication.
- Do not materialize the entire encrypted container or decrypted archive.
- Stream attachments directly into encrypted staging files.
- Never write attachment plaintext to persistent storage.
- Re-encrypt restored attachments using fresh local Tink keysets and the target device's Keystore.
- Preserve owner-bound AAD.
- Validate attachment size and SHA-256.
- Validate schema version, entity counts, IDs, relationships, and foreign keys.
- Prevent duplicate IDs and path collisions.
- Preserve additive restore semantics.
- Never roll back newer local records.

### Database consistency

Do not claim that a streaming implementation is atomic merely because it uses a Room transaction.

Evaluate whether large imports can safely fit into one transaction.

If necessary, implement a durable staged-import design with:

- Import identifier.
- Staging metadata.
- Durable journal.
- Explicit commit state.
- Recovery after process death.
- Cleanup of unreferenced staged files.
- Verification that no database row references a missing attachment.

A partially completed restore must never be reported as successful.

## What was built

**Streaming container** (`EncryptedBackupContainer.kt`) — `openWriter`/`StreamEncryptor` and `openReader`/`StreamDecryptor` (`readHeader`, `verifyBody`, `openPlaintext`, `read`, `finish`), all over the **unchanged KONNXBK2 byte layout** (AES-256-GCM, 64 KiB chunks, index-bound AAD, final marker, authenticated footer, same Argon2id/HKDF parameters). `verifyBody()` authenticates every chunk and the footer with the DEK before a single plaintext byte is exposed, then `openPlaintext()` re-reads with the same DEK — one Argon2 per restore. `inspect`, `verifyCredential`, both rewrap paths are streaming too; the legacy `encrypt()` now delegates, so there is one implementation of the format.

**Streaming export/restore** — new `BackupArchiveStream` writer/reader (bounded buffers, digest-per-entry, order-agnostic reading for old backups), `exportBackupFiles`/`restoreBackupFiles` in `LocalAttachmentStore`, `BackupEngineImpl` (temp encrypted file → fsync → verify → atomic publish; restore: verify → decrypt → parse → ciphertext-only staging → fresh Tink keyset re-encrypt → one chunked Room transaction), `BackupRecoveryEngineImpl` streaming `authenticate`, and WebDAV file-streaming upload/download.

**Limits** — 256 MiB/entry, 32 MiB payload, 1 MiB manifest, 64 KiB key envelope, 1 GiB total decompressed, 10 000 entries, 255-char names, `Math.addExact` throughout; traversal, duplicates, unmanifested entries and bombs rejected.

## Bugs found and fixed during verification

1. `StreamDecryptor.restart()` didn't reset `footerVerified` → every verify-then-decrypt flow failed.
2. Trailing bytes after the footer were accepted.
3. `ZipOutputStream` was being double-wrapped (nested ZIP) in the engine and instrumentation tests.
4. `BackupArchiveStreamReader` closed the plaintext stream it was handed, so the container could never be finalised — ownership now stays with the caller.

## Selected architecture

| Conversation | Cryptosystem | Implementation | Guarantees |
|---|---|---|---|
| Direct | PQXDH (X25519 + Kyber1024) → Double Ratchet, one session per **recipient device** | libsignal (AGPL gate) | per-message forward secrecy, DH-ratchet PCS, PQ handshake |
| Group | MLS RFC 9420, ciphersuite `0x0001`, one leaf per device | OpenMLS (MIT) via UniFFI | 1 ciphertext/message, epoch FS/PCS, **cryptographic** removal, no PQ |

One `KONNXEE1` envelope (116-byte big-endian header + opaque library ciphertext), deterministic CBOR payload with CDDL, header bound *inside* the authenticated payload because libsignal has no caller AAD. Boundary rule: one suite per conversation (`bindingId`); MLS Welcome/Commit travel in envelopes but no key or ratchet output ever crosses between protocols.

## Key findings from the audit

- 34 modules, `minSdk 26`, server schema v2 — and **no** device table, prekey table, envelope table, device key, or user cryptographic identity anywhere. Sync is account-scoped, so every device sees the same plaintext. Device identity today is only a local `dev-<uuid>` used for attachment owner AAD.
- The pre-existing `E2EE_ARCHITECTURE.md` is a sketch (single device, groups deferred); it is now superseded by the Phase 3.0 set while staying untouched so it keeps describing history honestly.
- Concrete compatibility trap found: Phase 2.6's archive reader **rejects unknown entry prefixes**, so backup archive schema 3 needs a tolerance change *before* any build writes E2EE metadata (U-11).
- Concrete gap found: account sessions aren't bound to `deviceUid`, so a revoked device keeps a valid bearer token (U-14b).

## Key design decisions (14 records, PDR-001…014)

No user-level private key exists — identity is an append-only signed **UIR hash chain** with pinned `(seq, entryHash)`; a lower seq is `E_ROLLBACK`, an equal seq with a different hash is `E_FORK`. Device linking transfers an **authorisation, never a private key** (QR + SAS). Own-device copies are mandatory. Backups contain **history only** — no keys, no sessions, no trust pins, so restore is always a new device. Metadata is documented, never promised away (no sealed sender/padding in v1).
