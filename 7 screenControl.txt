## What was built

**Transport:** the peer connection runs in the webview (Chromium under WebView2 — real ICE, DTLS-SRTP, SCTP), inside `apps/desktop/src/services/rtc.ts`. That controller (`RtcLink`) knows nothing about credentials, identity, signaling or sessions: it takes an approved session, a peer factory, a signal transport and timers, so it is fully testable and replaceable. Everything it may send is authorized in Rust, which keeps the security-relevant decisions out of injected JavaScript.

**Wire protocol:** `rtc.offer`/`rtc.answer`/`rtc.ice` now carry a `negotiationId` (minted by the core) and offers carry `restart`. `session.accept` no longer carries an ICE list — the relay issues it.

**Relay:** new `ice/` module issues STUN plus, when `SIGNALING_TURN_URLS`/`SIGNALING_TURN_SECRET` are set, a coturn REST credential (`<expiry>:<sessionId>` + HMAC-SHA1) that expires with the session. The hub relays `rtc.*` only inside a `ready` session, only to the other participant, only in the fixed direction (viewer offers, host answers), and drops frames quoting a stale negotiation.

**Rust core:** `networking/rtc.rs` holds the pure rules (direction, negotiation binding, size/control-character limits, CSPRNG negotiation ids); `client.rs` enforces them on both directions and relays through `send_rtc_signal`. The session token still never reaches the webview, the UI or a log.

**UI:** a session now shows "Securing link" until the encrypted channel is verified, "Connected over an encrypted peer-to-peer link" after, "Recovering…" during an ICE restart, and a failure ends the session instead of leaving a fake connected state.

**Two real bugs found while wiring this:** validation rejected every genuine SDP because `text()` forbids control characters and SDP is CRLF-separated; and candidates arriving before the host's answer were dropped, since the viewer could not know the negotiation id yet. Both are fixed and covered by tests.

## Bugs found and fixed

1. **The peer link never started (blocking bug).** `useSignaling`'s event subscription is registered once on mount, so it captured the first render's `startPeerLink`, whose `localDeviceId` was still `null` (credentials load asynchronously). It returned silently — no error, both sides stuck at "Establishing the encrypted peer link." Fixed with a `startPeerLinkRef` indirection. No unit test could have caught this; only the two-instance run did.
2. **Test isolation was impossible, and I clobbered the production credential record.** `APPDATA` does not affect Tauri's `app_data_dir` on Windows, so my first two "isolated" instances both used `%APPDATA%\com.miniremote.desktop` (same device ID, each rotating the shared credential file). Fixed by adding a `MINIREMOTE_DATA_DIR` override (absolute path only) in `lib.rs`, after which profiles were genuinely separate. **Disclosure:** the production `session-credentials.bin` was overwritten at 14:44 by a test-generated password; `identity.json` was untouched, and the app rotates its password on restart anyway, so the effect is a rotated password. The two test profiles were deleted afterwards.

## Known gap (reported, not fixed)

When the signaling server restarts during a live session, both apps keep showing "Connected over an encrypted peer-to-peer link" while the relay's record is gone (`sessions: 0`). The P2P link genuinely survives, but the UI then overstates *session* state. Recommendation: end the session when the signaling link is lost or re-established, or re-announce live sessions on reconnect.

## Key architectural decision (and its honest trade-off)

The only WebRTC stack in the product is Chromium inside WebView2. Keeping it (as required) means the **host webview must own the video track**, while frames must be captured natively in Rust. Therefore:

```
Host Rust:  WGC capture ─▶ D3D11 texture ─▶ Video Processor (BGRA→NV12, scaled)
            ─▶ Media Foundation H.264 encoder (HW MFT first, software MFT fallback)
            ─▶ AVCC samples + avcC config ─▶ per-session frame channel
                     │  invoke("next_video_frame") → raw ArrayBuffer (~2–4 Mbps, not 250 MB/s)
Host JS:    WebCodecs VideoDecoder ─▶ MediaStreamTrackGenerator ─▶ sender on the EXISTING RTCPeerConnection
Viewer JS:  existing PeerConnection "ontrack" ─▶ <video> in the viewer window
```

- **Why not raw frames over IPC:** 1080p BGRA is 8.3 MB/frame; even 720p30 NV12 is ~41 MB/s. Encoded transport is ~1–3 MB/s and keeps Rust the encoder of record (which the requirements ask for).
- **Cost that I will state plainly in the docs:** the host encode happens twice (Rust, then Chromium's WebRTC encoder). At the 720p/1080p profile caps with hardware on both sides this is acceptable; the alternative (moving the whole media stack to `webrtc-rs`) would replace the Phase 5 architecture and is explicitly out of scope.
- **Fallbacks:** if `MediaStreamTrackGenerator` is unavailable, paint into an offscreen canvas and use `canvas.captureStream(0)` + `requestFrame()`; if no MF H.264 encoder exists, streaming fails with a clear error rather than sending nothing (no fake frames, ever).

**Viewer window:** a separate Tauri window `viewer` (created only after approval + verified peer link). Because a `MediaStream` cannot cross JS contexts, the viewer window hosts the *viewer-side* `RtcLink` (module unchanged); Rust routes `rtc` events with `emit_to` to the window that owns the link (host → `main`, viewer → `viewer`). Main window keeps its compact layout and only shows status + “Open viewer / Stop sharing”.

## Implemented

**Stage 4 — WebRTC video transport.** Rust capture (WGC/DXGI) → Media Foundation H.264 → framed packets (`u32 LE header len | JSON | AVCC`) over a Tauri `Channel<Raw>` → host webview WebCodecs `VideoDecoder` → `MediaStreamTrackGenerator` → the **existing** Phase 5 `RTCPeerConnection`/session/auth. Viewer offers one `recvonly` video m-line; host adds its track before `createAnswer`, so sharing starts/stops without renegotiation. Headers carry keyframe flag, PTS/duration, and an `avcC` config packet; bounded queues drop stale delta frames and reset on keyframes. No BGRA crosses IPC.

Rationale (investigated first): WebView2 158 has `VideoDecoder`, `EncodedVideoChunk`, `MediaStreamTrackGenerator`, `RTCPeerConnection`, but **not** `RTCRtpSender.createEncodedStreams` or `RTCRtpScriptTransform` — so decode/re-encode in Chromium is the documented compatible fallback.

**Stage 5 — Viewer window.** Separate Tauri window created only for an approved viewer session; owns the session's single peer connection. Fit / 1:1 / fullscreen, HUD (resolution, FPS, bitrate, quality, profile, encoder, RTT/loss), Disconnect; destroyed on session end, relay loss, link failure or close. Main window stays 360×480.

Applied to both the MF encoder and `setParameters({maxBitrate,maxFramerate})`. HUD shows only `getStats()` values; encoder/profile arrive from the host over the DTLS data channel.

## Defects found and fixed by the integration run
1. **serde field names** — `rename_all` on an enum renames variants only, so every sample arrived as `pts_us` and the webview rejected it. Added `rename_all_fields` + a Rust test asserting `ptsUs`/`durationUs`.
2. **Viewer window policy** — the window couldn't signal at all (`send_rtc_signal` was main-only); added a session-bound viewer allowance.
3. **Window lifecycle** — opening during "requesting" and `close()` on a window still being created left an orphaned native window (IPC then failed with `failed to acquire webview reference`); now opens only on a ready session and uses `destroy()`.
4. **Peer identity lost** — relay status updates emitted `peer: null`, so the data-channel hello check rejected the host; `session_status` now carries the stored peer.

## Root cause of the approval requirement
It was the Phase 5 design, not a bug: the relay state machine was `authenticating → awaiting-approval → ready`, and the session token was minted only in `handleAccept`, with permissions taken from the `session.accept` payload (`mouse: true, keyboard: true`). The host therefore had to pick permissions by clicking Accept, so authentication alone could never admit a viewer.

## Root cause of the black screen
Two coupled lifecycle defects, both in that gate:

1. **`session.ready` depended on the approval step.** When that step failed or raced (e.g. Accept arriving before the server had processed the host's `auth.result`, which is exactly what my automated run hit), the relay answered `session-unavailable` and the session stayed unauthorised until it expired. Without `session.ready` there is no session token, no ICE list and no peer link — so the viewer window had nothing but a black surface.
2. **The window could report "Offline" while the Rust client was registered.** `connect_signaling` returned an error ("the signaling connection is already active") when the webview mounted after the core's startup connect, so `Connect` stayed disabled and no session could be started at all. Now it returns the live snapshot, and waits briefly for the link to settle.

With those removed/changed, the media path itself proved healthy end-to-end on this machine: I could not reproduce a black frame anywhere in WGC → NV12 → MF H.264 → AVCC → Channel → WebCodecs → MediaStreamTrackGenerator → WebRTC → `<video>`. So I did **not** invent a media-path fix; instead every stage now emits a structured, pixel-free line (`[video] host decoder configured`, `… published first decoded frame`, `… decoder failed`, `[video] viewer track`, `[video] viewer stats`) that pins a future failure to one stage. Documented in ARCHITECTURE §8.10 and the README troubleshooting table.
